# 18 Win32 パッケージリファレンス

## 18.1 概観

Win32 の実装はまだ開発の途上にあります。MIT Scheme が DEC Alpha アーキテクチャの Windows
NT に移植されると、変更が必要になると予想されます。とくに、現在のシステムは、NT
オペレーティングシステムの帰結である問題と、Intel x86 アーキテクチャの帰結である問題とを
十分に区別する形になっていません。

したがって、この文書は決定版ではなく、現在のシステムがどう働くかの概略を示すにすぎません。
システムの一部は変わるので、win32 システムを使って実装されるどのプロジェクトも、再実装の
段階を計画しなければなりません。

Win32 の実装はいくつかの構成要素を持ちます。

- 特別なマイクロコード基本手続き。
- 動的にリンクされるライブラリ（DLL）の手続きを呼ぶための外部関数インタフェース（FFI）。
- Edwin のためのインタフェース。
- Win32 パッケージは、Windows 3.1 と Windows NT 3.1 の環境の機能を使うサポートを提供します。
- デバイス独立ビットマップのユーティリティ。これらは win32 の Scheme グラフィックスの実装
  で使われます。（Scheme グラフィックスの実装はリファレンスマニュアルで説明しています。）

Win32 のサポートのすべての名前は win32 パッケージの一部であることに注意してください。名前は
`(win32)` 環境で束縛され、ユーザ環境やルート環境の束縛としては現れません。この効果として、
`(win32)` パッケージ環境またはその子環境で Win32 ソフトウェアを開発するほうがはるかに簡単
です。

## 18.2 外部関数インタフェース

Win32 外部関数インタフェース（FFI）は、動的にリンクされるライブラリ（DLL）の C で書かれた
手続きを呼ぶための、原始的でかなり単純なシステムです。カスタム DLL のユーザの手続きと、
システムの手続き（たとえば `MessageBox`）の両方が、同じ仕組みを使って呼ばれます。

警告: 現状の FFI には、信頼して使うのを難しくするいくつかの欠陥があります。FFI へのインタ
フェースと、FFI が使う仕組みの両方が、将来変えられると予想されます。私たちがこれとこの文書
を提供するのは、Scheme から Win32 の機能のいくつかにアクセスする早い出発点を人々に与える
ためだけです。実験でこれを使うなら、どんなフィードバックも歓迎します。

FFI は、Scheme のデータオブジェクトではなく C のデータ型を使う C の手続きを呼ぶために設計
されています。したがって、たとえば Scheme のリストを返す C の手続きを書いて呼ぶことはでき
ません。返されるオブジェクトはつねに整数（C のデータ構造のアドレスを表すかもしれません）に
なります。

警告: Scheme のコールバック手続きを C の手続きに渡そうとするのは、きわめて危険です。それは
実際の手続きではなく整数の「ハンドル」を渡すことによってのみ可能で、そうしても、コールバック
手続きの実行のあいだにガベージコレクションが起こると、Scheme のヒープのオブジェクトが動いて
しまいます。したがって、コールバックと文字列を持つ外部手続きで、コールバックを呼んだあと、
文字列の値はもはや妥当でないかもしれません。この遊びをするには、実装の深い知識が要ります。

FFI へのインタフェースは2つの主要な構成要素を持ちます。外部手続きに渡され、そこから返される
値の型を宣言する言語と、外部手続きを宣言するフォームです。

### 18.2.1 Windows の型

外部型は、Scheme の世界の中でオブジェクトを表すのに使われる Scheme のデータ型と、C の世界で
そのデータオブジェクトを表す C のデータ型とのあいだの対応を表すよう設計されています。したがって、
Scheme で真の C オブジェクトを操作することも、C で Scheme オブジェクトを操作することもでき
ません。

各外部型は、Scheme と C のオブジェクトのあいだの対応が保たれることを合わせて保証する4つの
側面を持ちます。これらの側面はすべて、妥当性を調べるか表現どうしを変換する手続きとして符号化
されます。したがって、外部型は宣言的な型というより、その型をどう渡すかの手続き的な記述です。
基礎となる外部手続き呼び出しの仕組みは、整数とベクタのような Scheme オブジェクトを渡せ、整数
の値を返します。他のすべてのオブジェクトは整数か他の基本型に翻訳されなければならず、整数から
復元されなければなりません。

側面は次のとおりです。

**check**
引数が受け入れられる Scheme の型なら `#t` を、そうでなければ `#f` を返す述語。check 手続き
は型検査に使われます。

**convert**
基本型の1つの Scheme オブジェクトを返す1引数の手続き。オブジェクトを、いずれ C オブジェクト
に変換される「より単純な」オブジェクトに変換するのに使われます。合法なより単純なオブジェクト
は整数と文字列です。

**return-convert**
整数を与えられると、check を満たす型の Scheme オブジェクトを返す1引数の手続き。その目的は、
外部手続きが返す結果を Scheme の値に変換することです。

**revert**
一部の C の手続きは1つ以上の引数を書き換えます。これらの引数は参照渡し、すなわちそのアドレス
へのポインタとして渡されます。Scheme オブジェクトは異なるメモリ配置と記憶の慣習を持つかも
しれないので、参照ではなくコピーインとコピーアウトで渡さなければなりません。revert は2つの
パラメータ、渡されたもとのオブジェクトと、そのオブジェクトに convert を適用した結果を取る
手続きです。revert は変換されたオブジェクトを調べ、変更をもとのオブジェクトに書き戻せます。

#### `define-windows-type name check convert return revert` 〔特殊形式＋〕
#### `define-similar-windows-type name model [check [convert [return [revert]]]]` 〔特殊形式＋〕

どちらのフォームも Windows の型を定めます。最初のフォームは、上で説明した側面を用いて型を
定めます。2番目は、ある側面を除いて別の型に似ているものとして型を定めます。その側面は定め
直されます。`name` は型の名前です。`model` は型の名前です。`check`、`convert`、`return`、
`revert` は手続きか値 `#f` です。`#f` は既定値を使うことを意味し、2番目のフォームでは
`model` に与えられた定義を使うことを意味します。既定値は次のとおりです。

**check** `(lambda (x) #t)`、すなわち検査なし。

**convert** `(lambda (x) x)`、すなわち翻訳を行わない。

**return** `(lambda (x) x)`、すなわち翻訳を行わない。

**revert** `(lambda (x y) unspecific)`、すなわち更新を行わない。

検査なしの Windows 型（下記）は次のように定められています。

```scheme
(define-windows-type unchecked #f #f #f #f)
```

Windows の型は第一級の値ではないので、変数に格納したり `define` を使って定めたりできません。

```scheme
(define my-type unchecked)                    error> Unbound variable
(define-similar-windows-type my-type unchecked)
                                            ;; 正しいやり方
```

Scheme の文字は整数に変換されなければなりません。これは次のように成し遂げられます。

```scheme
(define-windows-type char
    char?           ; check
    char->integer ; convert
    integer->char ; 返り値の変換
    #f              ; 参照渡しできない
)
```

#### `unchecked` 〔Windows 型〕

検査されず、Scheme の整数から C の整数への、または Scheme の文字列から文字列の最初のバイト
への C のポインタへの、基本的な変換だけを受ける型。返される unchecked の値は整数として返され
ます。

#### `bool` 〔Windows 型〕

Scheme の真偽値は C の整数 0 と 1 に相当します。Windows 型 `bool` は次のように定められて
います。

```scheme
(define-windows-type bool
    boolean?
    (lambda (x) (if x 1 0))
    (lambda (x) (if (eq? x 0) #f #t))
    #f)
```

#### `char` 〔Windows 型〕

Scheme の文字は、小さい整数と区別がつかない C の `char` 型のオブジェクトに変換されます。

#### `int` 〔Windows 型〕
#### `uint` 〔Windows 型〕
#### `long` 〔Windows 型〕
#### `ulong` 〔Windows 型〕
#### `short` 〔Windows 型〕
#### `ushort` 〔Windows 型〕
#### `word` 〔Windows 型〕
#### `byte` 〔Windows 型〕

変換なしに渡されるさまざまな整数型。

#### `string` 〔Windows 型〕

文字列の最初の文字への `char*` 型の C ポインタとして渡される文字列。

#### `char*` 〔Windows 型〕

文字列または `#f`。文字列は文字へのポインタとして渡されます。文字列は正しくヌル終端されます。
`#f` はヌルポインタとして渡されます。これは、C オブジェクトと Scheme オブジェクトのあいだに
より複雑な写像がある例です。C の `char*` 型は、その値に応じて2つの Scheme の型のどちらかで
表されます。これにより、空の文字の列を指す C の文字列（ポインタ）と、（どこも指さない）ヌル
ポインタとを区別できます。

#### `handle` 〔Windows 型〕
#### `hbitmap` 〔Windows 型〕
#### `hbrush` 〔Windows 型〕
#### `hcursor` 〔Windows 型〕
#### `hdc` 〔Windows 型〕
#### `hicon` 〔Windows 型〕
#### `hinstance` 〔Windows 型〕
#### `hmenu` 〔Windows 型〕
#### `hpalette` 〔Windows 型〕
#### `hpen` 〔Windows 型〕
#### `hrgn` 〔Windows 型〕
#### `hwnd` 〔Windows 型〕

さまざまな種類の Win32 ハンドル。これらの名前は、Windows の C 言語ヘッダファイルの同じだが
すべて大文字の名前に対応します。Win32 API の呼び出しがこの型の値の出どころで、値は他の Win32
API の呼び出しへの引数としてを除けば意味を持ちません。現在これらの値は整数として表されます
が、Win32 ハンドルは将来、割り当てられた Scheme オブジェクト（たとえばレコード）で表され、
述語（たとえば `hmenu?`）と、ガベージコレクタとのほどよい連動を可能にして、現在の面倒な
ハンドルの割り当てと解放からプログラマを解放すると予想されます。

#### `resource-id` 〔Windows 型〕

Windows のリソース識別子は、小さい整数か文字列のどちらかです。C では、ポインタがより大きい
整数のように見えるので、この区別が可能です。小さい整数を表す機械のワードは、リソースの名前
のテキストへのポインタである機械のワードと区別できます。

### 18.2.2 Windows の外部手続き

外部手続きは、モジュール（ふつう動的にリンクされるライブラリ（DLL））の中の、呼び出せる
エントリポイントとして宣言されます。

#### `find-module name` 〔手続き＋〕

`windows-procedure` で手続きを作るのに使うのに適したモジュールを返します。`name` は DLL
ファイルの名前である文字列です。内部で `find-module` は `LoadLibrary` Win32 API を使うので、
`name` はこの呼び出しの仕様に従うべきです。`name` は、DLL の完全なパス名か、Scheme のバイナリ
`SCHEME.EXE` と同じディレクトリかシステムディレクトリにある DLL の名前のどちらかであるべき
です。

返されるモジュールは DLL の記述で、DLL はこの呼び出しの時点やその直後に必ずしもリンクされる
必要はありません。DLL モジュールは、必要に応じてリンクされ、Scheme が終了する前と、ガベージ
コレクションのあとにエントリポイントへの残りの参照がないときにリンク解除されます。このふるまい
は、DLL が実際に使われない（すなわち DLL の手続きを呼ぼうとしない）かぎり、DLL が欠けていても
Scheme システムが走れることを保証します。

#### `gdi32.dll` 〔変数＋〕

この変数は、`LineTo` などの Win32 API のグラフィックス呼び出しを含む `GDI32.DLL` ライブラリ
を記述するモジュールに束縛されています。

#### `kernel32.dll` 〔変数＋〕

この変数は、`KERNEL32.DLL` ライブラリを記述するモジュールに束縛されています。

#### `user32.dll` 〔変数＋〕

この変数は、`USER32.DLL` ライブラリを記述するモジュールに束縛されています。このモジュールは、
`MessageBox` や `SetWindowText` のような多くの役立つ Win32 API の手続きを含みます。

#### `windows-procedure (name (parameter type) …) return-type module entry-name [options]` 〔特殊形式＋〕

このフォームは手続きを作り、「外部の named-lambda」と考えられます。このフォームは、`module`
の値が識別するモジュールの、エクスポートされたエントリポイント `entry-name` が識別する C の
手続きを呼ぶ Scheme の手続きを作ります。`entry-name` と `module` は手続きの作成時に評価される
ので、どちらも式でよいです。`entry-name` は文字列に評価されなければならず、`module` は
`find-module` が返すモジュールに評価されなければなりません。これらは、フォームのうち手続きの
作成時に評価される唯一の部分です。

`name` は手続きの名前で、記録の目的のためだけのものです。このフォームは `name` という名前の
手続きを定めません。むしろ `lambda` に似ています。`name` はデバッグやプリティプリントに使われ
るかもしれません。

Windows の手続きは固定数のパラメータ（すなわち「残余」パラメータや「可変引数」はありません）
を持ち、その各々は名前が付き、Windows 型 `type` に結びつきます。`name` パラメータと Windows
型 `type` はどちらもシンボルでなければならず、評価されません。手続きは Windows 型 `return-type`
の値を返します。

次の例は、ウィンドウハンドル（`hwnd`）と文字列を取り、真偽値（`bool`）の結果を返す手続きを
作ります。手続きは、変数 `user32.dll` の値であるモジュールの `SetWindowText` エントリを呼ぶ
ことでこれを行います。変数 `set-window-title` はこの手続きをその値として持つよう定められます。

```scheme
(define set-window-title
  (windows-procedure
   (set-window-text (window hwnd) (text string))
   bool user32.dll "SetWindowText"))

(set-window-title my-win "Hi")
                         ⇒ #t
                         ;; ウィンドウのタイトル/テキストを変える

set-window-title              ⇒ #[compiled-procedure ...]
set-window-text                error> Unbound variable
```

オプションがなければ、作られた手続きは (a) 引数を型に照らして検査し、(b) 引数を変換し、(c) C
の手続きを呼び、(d) 返された値を変換します。型の1つに reversion が定められていても、reversion
は行われません。（reverted な型はまれ〔私は一度も使ったことがない〕なので、使わないのにこれ
にコストを払うのはばかげているようです。）

次のオプションが許されます。

**`with-reversions`**
reversion が型の変換に含まれます。

**`expand`** `with-reversions` の同義語。

**Scheme コード**
Scheme コードが、既定の過程の (a) と (b) のステップのあいだに置かれます。Scheme コードは、
引数への制約を、引数どうしの制約（添字が文字列の妥当な位置を指すかの検査など）を含めて、
強制できます。

両方のオプション（すなわち `with-reversions` と Scheme コード）が使われるなら、
`with-reversions` が先に現れなければなりません。任意個の Scheme の式を置けます。

### 18.2.3 Win32 API の名前と手続き

この節は動く標的です。

`wingdi.h` と `winuser.h` の `#define` の値は、`(win32)` パッケージ環境で束縛として利用でき
ます。`#define` のシンボルはすべて大文字です。これらはすべて小文字の Scheme 識別子に翻訳
されており、したがって `WM_LBUTTONUP` は Scheme 変数 `wm_lbuttonup` です。Scheme は大文字
小文字を区別しないので、大文字の版が使え、コードをふつうの Windows のコードに近く見せるため
おそらくそうすべきです。Scheme の束縛は自動的に作られています。`#define` のシンボルのほとんど
はアンダースコアを含むので、名前の衝突は多くありません。ただし、1つの非常に目立つ名前の衝突
があります。`ERROR` は 0 に `#define` されており、ルートパッケージ環境の Scheme 手続き
`error` を覆い隠します。エラーを通知するには、`access` を使ってシステム大域環境から `error`
を取ります。

```scheme
(declare (usual-integrations))
...
((access error system-global-environment) "Complain" ...)
```

手続きの集合は不完全です。手続きは、システムの他の部分（たとえば Scheme グラフィックス）の
実装のために必要に応じて加えられてきたからです。詳細は実装を見よ。

Win32 API の手続きの名前は、次のように一様に Scheme 識別子に変換されています。

- 先頭の大文字は小文字に翻訳されます。
- 続く大文字の列は、ハイフン（マイナス記号）が前に付いた小文字に翻訳されます。すなわち、
  小文字から大文字への移り目にハイフンが挿入されます。
- `Is` で始まる述語には、最後に疑問符が付けられます。

例: これらの規則を `IsWindow` に適用すると `is-window?` になり、`GetDC` は `get-dc` に翻訳
されます。

## 18.3 デバイス独立ビットマップのユーティリティ

デバイス独立ビットマップ（DIB）のユーティリティライブラリ `DIBUTILS.DLL` と、Win32 システム
のソースの `dib.scm` の結びついた手続きは、外部関数インタフェースを使って Scheme でない
オブジェクトにアクセスして操作する方法の例です。

#### `dib` 〔Windows 型〕

C の世界では、DIB は、画像についての情報と画像のピクセルを表すビットを含むメモリの一片への
ハンドルです。ハンドルは機械のワードの大きさのデータの一片で、32 ビットの整数と考えられます。
ハンドルはヌル（すなわちゼロ）でありえ、DIB を記述するメモリのブロックがないことを示します。
ヌルの値は、ふつう DIB を作るはずだが、メモリを割り当てられなかった、ファイルを開けなかった
などの何らかの理由で失敗した C 関数が返します。

Scheme の世界では、DIB はビットマップについての情報（具体的にはハンドルを表す整数）を含む
構造です。ヌルハンドルのエラー値を映すために、dib の Windows 型に `#f` も含めます。

```scheme
(define dib-result
  (lambda (handle)
    (if (= handle 0)
        #f
        (make-dib handle))))

(define dib-arg
  (lambda (dib)
    (if dib
        (cell-contents (dib-handle dib))
        0)))

(define-windows-type dib
  (lambda (thing) (or (dib? thing) (eq? thing #f)))
  dib-arg
  dib-result)
```

### 18.3.1 DIB の手続き

次の手続きは、`windows-procedure` と同じ慣習を使って、型の付いたパラメータを持ちます。

#### `open-dib (filename string)` 〔手続き＋〕

返り型: `dib`。`DIBUTILS.DLL` の `OpenDIB` エントリを呼びます。返り値が `#f` でなければ、
ファイル `filename` が見つかり、正常に開かれ、内容がデバイス独立ビットマップとしてメモリに
読み込むのに適していました。

#### `write-dib (filename string) (dib dib)` 〔手続き＋〕

返り型: `bool`。`DIBUTILS.DLL` の `WriteDIB` エントリを呼びます。ファイル `filename` を開いて
書き込めれば `#t` を返します。この演算のあと、ファイルは、`open-dib` やビットマップエディタ
のようなさまざまなシステムユーティリティが理解する標準の形式のビットマップデータを含みます。
失敗に至るどんな問題も `#f` の返り値で通知されます。

#### `bitmap-from-dib (dib dib) (palette hpalette)` 〔手続き＋〕

返り型: `hbitmap`。`DIBUTILS.DLL` の `BitmapFromDib` エントリを呼びます。返される値はデバイス
依存ビットマップです。DIB の色は `palette` の色に照合されます。

#### `dib-from-bitmap (bitmap hbitmap) (style dword) (bits word) (palette hpalette)` 〔手続き＋〕

返り型: `dib`。デバイス依存ビットマップ `bitmap` と同じ画像を含む DIB を返します。`style` は
DIB の種類、たとえば圧縮の様式を決めます。`DIBUTILS.DLL` の `DibFromBitmap` エントリを呼び
ます。

#### `dib-blt (dest hdc) (x int) (y int) (w int) (h int) (src dib) (src-x int) (src-y int) (raster-op long)` 〔手続き＋〕

返り型: `bool`。`DIBUTILS.DLL` の `DibBlt` エントリを呼びます。Win32 API の `BitBlt` 呼び出し
に似ていますが、別のデバイスコンテキストの一片ではなく DIB を描きます。dib をデバイスコンテキスト
`hdc` の位置 `(x,y)` に描きます。幅 `w` 高さ `h` の矩形が dib の位置 `(src-x,src-y)` から複製
されます。`raster-op` は source と destination を組み合わせられるようにするはずですが、私は
これを正しく作れなかったと思うので、`SRCCOPY` に留めてください。

#### `%delete-dib (dib-handle handle)` 〔手続き＋〕

返り型: `bool`。`DIBUTILS.DLL` の `DeleteDIB` エントリを呼びます。パラメータが dib ではなく
ハンドルであることに注意してください。これにより、dib レコードを必要とせず、ハンドルの値だけ
を知って、DIB を破棄してそのメモリを回収できます。この重要性は、dib レコードが GC されると、
GC フックがハンドルだけを知って記憶域を回収できることです。

#### `delete-dib (dib dib)` 〔手続き＋〕

返り型: `bool`。この手続きは `%delete-dib` を呼んで、DIB が占める記憶域を回収します。削除
されたあと、DIB は使うべきではありません。この手続きは、プログラマが、次のガベージコレクション
の前に外部ヒープの記憶域が尽きる危険を冒すのではなく、それを回収できるようにします。

#### `dib-height (dib dib)` 〔手続き＋〕

返り型: `int`。`DIBUTILS.DLL` の `DibHeight` expand エントリを呼びます。ビットマップの高さを
ピクセルで返します。

#### `dib-width (dib dib)` 〔手続き＋〕

返り型: `int`。`DIBUTILS.DLL` の `DibWidth` エントリを呼びます。ビットマップの幅をピクセルで
返します。

#### `copy-bitmap (bm hbitmap)` 〔手続き＋〕

返り型: `hbitmap`。`DIBUTILS.DLL` の `CopyBitmap` を呼びます。もとと同じ大きさと内容の新しい
ビットマップを作ります。

#### `create-dib (width int) (height int) (style int) (depth int) (palette hpalette)` 〔手続き＋〕

返り型: `dib`。`DIBUTILS.DLL` の `CreateDIB` エントリを呼びます。`width` × `height` ピクセルで、
`depth` ビットの色情報の DIB を作ります。`style` パラメータはビットマップがどう格納されるか
を決めます。私は `BI_RGB` しか使ったことがありません。`depth ≤ 8` なら、`palette` が DIB の
色表を決めます。

#### `crop-bitmap (bm hbitmap) (left int) (top int) (right int) (bottom int)` 〔手続き＋〕

返り型: `hbitmap`。`DIBUTILS.DLL` の `CropBitmap` エントリを呼びます。もとの領域の画像を含む
新しいビットマップを返します。

#### `dib-set-pixels-unaligned dib (pixels string)` 〔手続き＋〕

返り型: `bool`。`DIBUTILS.DLL` の `DIBSetPixelsUnaligned` エントリを呼びます。`pixels` の
バイトをビットマップに詰め込みます。`pixels` に整列の制約はありません（これを行うふつうの
方法は `SetDIBits` 関数を使うことですが、これはビットマップの各走査線が、走査線が4バイトの
倍数の長さでなくても、32 ビットワードに整列されていることを要求します）。

### 18.3.2 DIB ユーティリティの実装のその他の部分

`DIBUTILS.DLL` ライブラリはふつうの DLL です。DLL の作り方については標準の Microsoft Windows
の文書を見よ。Scheme ソースの `WIN32/DIBUTILS` ディレクトリのコードを見てください。

次に注意してください。

- 外部関数インタフェースが手続きを見つけるには、それらが `.DEF` 定義ファイルでエクスポート
  として宣言されていなければなりません。
- `.DLL` ファイルを読み込むには Scheme 関数 `find-module` を使います。これがどう行われるかは
  `WIN32/DIB.SCM` を見てください。
- 現在のシステムは `__stdcall` と `__cdecl` の呼び出し規約の C の手続きで働きますが、
  `__fastcall` の呼び出し規約では働きません。
